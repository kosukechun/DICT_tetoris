# 設計と通信仕様

## ゲーム

`shared/engine.js` がサーバー側の確定ルールを管理します。横9×縦15、4個の色付きブロックを落として、上下左右の同色4個以上を消します。両者は同じシードとブロック生成順を使い、お邪魔の配置乱数は独立しています。

攻撃と予告スタックは `MAX_GARBAGE`／`MAX_PENDING_GARBAGE`（ともに6個）までに制限し、自分の `pending` を優先して相殺し、差分だけ `onAttack` で送信します。両者の処理順を入れ替えても、同量の攻撃は相殺され、差分のみが残ることをテストします。`cancellation` に単調増加の通知ID、相殺数、元の予告、残り予告、送り返した数を記録します。クライアントは新しいIDのときだけ盤面上に大きな通知を0.25秒表示し、同じスナップショットの繰り返し受信で演出を再開しません。

お邪魔の単位は1セルです。最初の予告から1.2秒経過後、消去しなかった固定で最大6個の落下処理を開始します。各ブロックは0.15秒で落下し、0.05秒空けて次を落とします。40msのサーバー更新刻みを含め、6個の落下待ちが1.5秒以内に終わることをテストします。`pending` は未着地分を含めて最大6個です。落下中は移動・落下を待ち、回転入力は次のブロックへ予約し、シールドはすぐ受け付けます。既存ブロックをせり上げず、空いている列の一番上に積みます。天井到達で敗北です。

CPUの配置間隔はEASYが2400ms、NORMALが1600ms、HARDが900msです。配置評価の乱数幅はそれぞれ28／16／8とし、全難易度で速度と配置精度を控えめにしています。

オンライン戦・CPU戦とも開始から5分で終了します。時間切れでは各 `board` の0以外のセルを数え、少ない側を勝者、同数を引き分けにします。スコアや操作中のブロックは判定に使いません。自動落下は全時間帯で650ms間隔を維持し、経過時間で短縮しません。

チートモードのパスワード `tomo` はWebSocketでサーバーへ送り、サーバー側で一致を判定します。有効化した席から相手へ5秒ごとに2個を `receive` し、通常のお邪魔上限・予告・相殺・シールド規則をそのまま適用します。パスワードは対戦履歴・イベント・標準出力へ保存せず、有効だった席と `cheat_attack` イベントだけを記録します。

色消去の初回判定は固定したブロックが属するグループだけを対象にします。連鎖中は消去で重力が働いた列だけを次の判定対象にするため、離れた既存グループが一度の固定をきっかけに大量消去されません。回転は左右だけでなく上方向にもキックし、床際の縦回転を受け付けます。

40msごとにゲームを更新し、約80msごとに状態を送信します。描画は受信した `fallingGarbage` を補間し、サーバーの盤面確定を変えずに滑らかにします。落下時間をまたぐ大きなtickでも、一度に複数個を着地させません。

PCの対戦画面はビューポート高に合わせたflexレイアウトです。対戦中は通常のヘッダーを省き、操作案内・作者名まで画面内に収めます。ResizeObserverで盤面に使える高さと横幅を測り、9×15の比率を保って表示します。下長押しは初回待ち80ms・反復60msです。PCの代表的な6解像度で、縦横のスクロールと盤面の比率をブラウザーテストで確認します。

公式ぷよぷよテトリスの完全再現ではありません。形、攻撃量、連鎖処理、盤面、落下時間は独自設定です。SRS、ホールド、Tスピン、試合への再接続は未実装です。

## 名前と履歴

`POST /api/register` は `nickname` のみを受け付けます。初回はサーバーでUUIDを作り、再登録は有効なCookieの本人の名前を更新します。同名の別ブラウザーは別プレーヤーです。試合・待機中の改名は拒否します。

32バイトのランダムなセッショントークンをHttpOnly／SameSite=Strict Cookieへ保存します。本番ではSecureも付きます。DBにはトークンのSHA-256ハッシュだけ保存します。有効期間は365日で、登録・改名時にCookieを更新し、旧トークンを失効させます。有効なCookieを持つ従来のプロフィールも改名時に同じ内部IDを引き継げます。Cookieを失った旧アカウントのID・パスワードでの再ログイン機能はありません。

| API                  | 内容                                          |
| -------------------- | --------------------------------------------- |
| `GET /health`        | 生存確認                                      |
| `POST /api/register` | 名前の登録／改名、Cookie発行                  |
| `POST /api/logout`   | セッションを失効し、接続を切断。APIとして提供 |
| `GET /api/me`        | プロフィール、未登録時はnull                  |
| `GET /api/history`   | Cookie本人の直近20試合。未登録は401           |

名前は文字列・空白以外1〜16文字。登録はIPごとに1分20回まで。変更操作とWebSocketは同一Originに限定します。WebSocketは同じ内部IDにつき1接続、1秒45メッセージ、1KBまで。CloudFront用の `ORIGIN_SECRET` を設定すると、`/health` を除き所定のヘッダーがないHTTP／WebSocket接続を拒否します。合言葉やトークンはログに出しません。

## 対戦通信

`/ws` へCookie付きで接続します。

```json
{ "type": "join", "mode": "cpu", "difficulty": "normal" }
```

オンラインは `mode: "online"`。操作は `{ "type": "action", "action": "left" }` の形式で、`left`, `right`, `rotate`, `down`, `drop`, `shield`, `forfeit` を受け付けます。待機取消は `{ "type": "cancel" }`。チート切替は `{ "type": "cheat", "password": "..." }`、OFFは `{ "type": "cheat", "enabled": false }` です。

サーバーのイベントは `ready`, `queued`, `canceled`, `cheat`, `start`, `state`, `result`, `saved`, `error`。開始前は3秒のカウントダウン。ping／pongで切断を検出します。

## 保存

| データ     | pk                         | sk                |
| ---------- | -------------------------- | ----------------- |
| プレーヤー | `USER#内部ID`              | `PROFILE`         |
| セッション | `SESSION#トークンのSHA256` | `SESSION`         |
| 対戦履歴   | `USER#内部ID`              | `MATCH#日時#UUID` |

ローカルはJSONファイルを直列更新し、一時ファイルからrenameで置換します。AWSはDynamoDB。同じキーの構造を使い、セッションの `ttl` は読み取り時にも確認します。試合イベントは最大1,500件で、消去・相殺・攻撃・お邪魔の個別着地などを記録します。

終了時に両プレーヤーの履歴を保存します。2人分はトランザクションではないため片側だけ成功する可能性があり、エラーは両者へ通知します。通常終了では進行中試合も引き分けとして保存します。強制終了・障害時の進行中試合は失われる場合があります。

## AWS

コンソールからCloudFormationでVPC・公開サブネット・DynamoDB・IAMロールを作成し、BeanstalkのNode.js 22へ専用ZIPをアップロードします。CloudFrontでHTTPSのURLを発行します。CloudFront→nginxの2段のプロキシなので `TRUST_PROXY=2`。設定ファイルでWebSocketを8080番のNodeプロセスへ転送し、アプリ・デプロイ・nginxログをCloudWatch Logsへ7日間保存します。構成図とログの見方は[README](../README.md#aws構成とログの見方)に記載します。

対戦部屋と待機列はプロセス内にあるため1インスタンスを維持し、デプロイはAll at onceにします。停止を許容する小規模利用向けです。台数追加には部屋・待機列の共有化が必要です。CloudFormationはDynamoDBを削除時も保持します。完全撤去時は手動削除が必要です。
